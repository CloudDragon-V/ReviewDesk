## 本轮怎样复现

原 `online_v1` 保存的是脱去身份元数据的“产品接受并合并后的发现”，没有保存原始 HTTP 响应或模型完整返回体。本轮只能回放其中保留下来的模型发现，无法恢复第一版产品已经过滤或合并掉的输出。

回放脚本先检查首次题库承诺及两轮 `RESULT_COMMITMENT.json`，然后核对 `analysis.py`、`context.py` 与原在线候选的哈希一致。使用当前本地分析器重新处理同一组合成源码，要求其结果与原 Candidate-A 逐字段完全相等，才允许恢复匿名化时移除的静态 `rule_id`。从原 Candidate-B 中扣除这些本地发现后，余下的已接受模型发现交给**最终产品函数** `service.merge_findings`，没有另写一套测评专用去重规则。

输出保留原 `item_id` 及原文，原独立评分判断逐条原样继承；只有被产品合并掉的项不再进入评分。脚本会拒绝当前本地发现变化、回放产生新发现或改变原发现文本等情形，避免对没有重新判断的内容套用旧评价。评分报告中的 `independent_adjudication: true` 表示使用了**原独立判断**，不表示本轮新进行了一次独立盲评分。

## 保留的能力边界与语义争议

首次本地规则测评的三项遗漏继续保留在原报告中：静默 `OSError` 处理、`shell=True` 配合字符串拼接、硬编码合成 API 密钥。本轮只修复结果合并，不新增检测规则，也不把脱敏成功等同于已经产生硬编码密钥审查提示。

其中 `except OSError: pass` 的 oracle 将“静默丢失失败信息”作为应提示的风险；这个判断存在产品语义前提。如果函数承诺保存必须成功，吞掉错误会使调用方难以获知失败；如果它明确提供尽力而为、可忽略失败的操作，忽略某些 `OSError` 也可能是有意行为。合成案例没有完整业务契约，因此 **FN 是相对冻结 oracle 的漏提示，不应宣称已经证明它在所有业务语境下都是缺陷**。本轮保持该目标与 FN 计数，不通过删除争议目标重新计算更高分数。

同样，shell 拼接与动态执行应结合输入信任边界判断，不能仅凭模式匹配就断言存在可被外部攻击者利用的漏洞。小规模合成样本上的分数不能替代真实项目人工复核。
