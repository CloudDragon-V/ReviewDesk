# 同类软件与技术路线调研

调研时间：2026-09-11

## 调研边界

本文关注与本项目直接相关的五类能力：AI 代码审查、静态分析融合、仓库上下文选择、代码关系图、token 与费用统计。

资料优先使用产品官方文档、官方技术文章、开源仓库和论文。商业产品没有公开的内部算法只能描述其公开宣称的流程，不能把推测写成已证实实现。

## 先说结论

公开资料中的成熟产品大多不是“把代码和提示词直接发给大模型”，而是采用下面的流水线：

```text
触发审查
  -> 确定范围（diff、文件、目录或整个仓库）
  -> 本地确定性分析（AST、符号、依赖、lint、SAST）
  -> 按 token 预算选择相关上下文
  -> 注入团队规则、任务意图和审查提示
  -> 调用一个或多个模型
  -> 解析结构化结果
  -> 校验路径、行号、证据并过滤低价值结论
  -> 在 PR、IDE 或桌面界面展示
  -> 保存反馈、耗时、token、费用和提示版本
```

因此，prompt/skill 只是系统中间的一层。真正决定质量的通常是上下文选择、确定性工具证据、输出校验和反馈闭环。

## 代表性产品和开源项目

| 产品/项目 | 主要场景 | 公开可验证的实现方向 | 对本项目的参考价值 |
| --- | --- | --- | --- |
| GitHub Copilot Code Review | PR、IDE 中审查变更 | 支持仓库级、路径级指令，支持 `AGENTS.md`、review skill 和 MCP；在临时开发环境中运行，可输出可应用的行级建议 | 说明“通用规则 + 路径规则 + 外部上下文”是成熟做法 |
| PR-Agent | 开源 PR 审查机器人 | 以 diff 为核心，做 token-aware 压缩；不同工具有独立 TOML prompt；把 Pydantic 字段描述放进提示，要求模型返回 YAML；支持多 Git 平台和多模型 | 最接近可复现的开源参考，可研究其 prompt、配置和结果模型 |
| CodeRabbit | 商业 PR/IDE/CLI 审查 | 官方公开称其结合定义/引用图、共同变更历史、语义索引、团队规则、lint/SAST 和验证脚本，再发布有证据的评论 | 代表“深上下文 + 工具验证”的高阶路线，但完整内部实现未开源 |
| Semgrep Assistant | 安全问题分诊和修复 | 先由确定性静态分析产生 finding，再用依赖、历史修复等上下文做 LLM 分诊和修复，之后用第二条链验证修复 | 证明“工具先找证据，模型负责解释和判断”比纯 LLM 更稳 |
| SonarQube | 规则、污点分析、架构约束 | 基于规则和数据流确定性地产生 bug、maintainability、security 等问题；提取结构和依赖并与目标架构比较 | 类别和严重程度应分开；关系和循环依赖应尽量本地计算 |
| Sourcegraph Cody | 大型代码库理解与辅助 | 组合关键词搜索、Sourcegraph 搜索和 Code Graph，为模型检索相关代码 | 说明单一向量检索不够，结构关系和传统搜索仍然重要 |
| Aider Repo Map | 大仓库代码编辑上下文 | 用 tree-sitter 提取符号和引用，构造仓库地图，再按依赖图重要度和 token 预算只发送关键部分 | 非常适合借鉴本项目的“上下文构建器” |
| Pyan3 / code2flow / pydeps | Python 调用与依赖图 | 通过 AST、名称绑定或导入信息近似生成函数/模块关系，再输出 DOT、SVG 或文本 | 可作为本地关系图的算法参考，同时必须承认动态调用误差 |
| Langfuse | LLM 可观测性 | 每次生成记录模型、输入/输出/缓存 token、费用、延迟和 prompt 版本；优先使用提供商返回用量，缺失时按价格表推算 | 适合借鉴本项目的调用记录和费用模型，无需第一版引入其平台 |

## 方向一：以 Git diff 为中心的 PR 审查

GitHub Copilot、PR-Agent、CodeRabbit 的主流入口都是 pull request 或本地未提交变更。它们先限定“本次新增或修改了什么”，再决定需要补充哪些仓库上下文。

GitHub Copilot 允许仓库级和路径级审查规则，还可接入 review skills 与 MCP。官方文档也说明其审查在临时开发环境运行，并把评论定位到代码位置。[GitHub Copilot Code Review 官方文档](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review)

PR-Agent 的开源 prompt 明确要求重点审查 diff 中新增的行，提醒模型它只看到部分代码，不要假设其他定义不存在；它把文件、起止行、问题说明等字段写成 Pydantic 风格定义，并要求只返回合法 YAML。[PR-Agent reviewer prompt](https://github.com/The-PR-Agent/pr-agent/blob/main/pr_agent/settings/pr_reviewer_prompts.toml)

这种实现的优点是输入小、行号准确、结果容易展示在 PR 中；缺点是可能漏掉旧代码和跨文件影响。CodeRabbit 也明确指出只看 diff 不足，因此会沿定义、引用和历史共同变更关系补充文件。[CodeRabbit 大型代码库审查说明](https://www.coderabbit.ai/blog/how-coderabbit-delivers-accurate-ai-code-reviews-on-massive-codebases)

对本项目的启发：第一版应支持“选择代码/文件/项目”模式；当项目进入 Git 仓库后，再增加“仅审查当前 diff”作为快速模式。

## 方向二：上下文工程，而不是全仓库直传

大型项目无法把所有文件完整发送给模型，常见做法是先建立轻量索引，再按任务选取片段。

Sourcegraph Cody 公开的上下文来源包括关键词搜索、Sourcegraph 搜索和 Code Graph，说明成熟产品通常同时使用文本检索和结构关系。[Sourcegraph Cody Context](https://sourcegraph.com/docs/cody/core-concepts/context)

Aider 的公开实现更具体：

1. 用 tree-sitter 提取文件中的类、函数、签名、定义和引用。
2. 构造文件依赖图。
3. 用图排序选择重要符号。
4. 只保留能放入用户 token 预算的仓库地图。

Aider 文档给出的默认 repo map 预算是 1k tokens，并强调完整文件会浪费上下文。[Aider Repo Map 技术说明](https://aider.chat/2023/10/22/repomap.html)

CodeRabbit 官方称它还会加入语义索引、相似实现、相关测试、历史 PR、工单意图和团队规则。这属于厂商公开说明，具体排序权重和实现细节未公开。[CodeRabbit Context Engineering](https://www.coderabbit.ai/blog/context-engineering-ai-code-reviews)

对本项目的启发：上下文构建器应成为独立模块，至少比较三种策略：

- 直接截断。
- 函数/类级 AST 分块。
- 基于 import、调用和引用关系的依赖扩展。

语义向量检索可以后加，不应成为第一版运行的前提。

## 方向三：静态分析与 LLM 混合

纯静态分析善于发现规则明确、可以证明的数据流问题；LLM 善于解释业务语义、判断意图和生成易读建议。成熟安全产品会把两者串起来。

SonarQube 将问题区分为 reliability、maintainability、security 和 security hotspot，并利用污点分析展示不可信输入从 source 到 sink 的路径。[SonarQube 安全规则与污点分析](https://docs.sonarsource.com/sonarqube-server/user-guide/rules/security-related-rules)

Semgrep Assistant 官方公开的流程是：确定性扫描结果、项目依赖和历史修复进入 prompt chain，LLM 进行分诊和修复，再由二次审查链检查漏洞是否仍存在、代码是否损坏以及修复是否完整。[Semgrep Assistant 技术说明](https://semgrep.dev/blog/2024/the-tech-behind-semgrep-assistant/)

CodeRabbit 也公开称其将 linter/SAST 结果纳入审查，并在需要时生成 shell/Python 检查来验证假设。[CodeRabbit 验证流程](https://www.coderabbit.ai/blog/how-coderabbit-delivers-accurate-ai-code-reviews-on-massive-codebases)

对本项目的启发：

- AST 能确定的事实先由本地程序产生，例如语法错误、导入、定义、调用边和部分未使用符号。
- LLM 不应重新猜测这些事实，而应基于事实解释风险和给出建议。
- LLM 独立提出的问题必须带触发条件、代码证据、路径、行号和置信度。
- 高风险发现可以增加本地复核器或第二次模型验证，但不必第一版全部实现。

## 方向四：代码关系图和“思维导图”

代码图大致分三层：

| 图层 | 节点 | 边 | 适合回答的问题 |
| --- | --- | --- | --- |
| 模块依赖图 | 包、模块、文件 | import、依赖 | 哪些模块耦合、是否循环依赖 |
| 符号调用图 | 类、函数、方法 | defines、uses、calls | 改这个函数会影响谁 |
| 控制/数据流图 | 语句、变量、条件 | control flow、data flow | 某输入如何流向危险调用 |

Pyan3 使用 Python AST 中的定义、名称绑定和 `ast.Load` 使用关系生成静态调用图，并能输出 GraphViz、SVG、HTML 或文本。[Pyan3 官方仓库](https://github.com/Technologicat/pyan)

code2flow 同样先生成 AST、查找函数与调用，再用名称和作用域启发式连接边；其文档明确说明动态语言无法得到完美静态调用图。[code2flow 官方仓库](https://github.com/scottrogowski/code2flow)

因此，本项目不应让 DeepSeek凭空生成关系图。推荐本地生成节点和边，DeepSeek只负责：

- 给复杂子图生成摘要。
- 解释为什么某条依赖值得关注。
- 将自然语言问题映射到需要高亮的节点。

界面再用 PySide6 `QGraphicsScene/QGraphicsView` 展示本地结果。图中的每条边需要带 `source`、`target`、`relation_type`、证据文件和行号。

## 方向五：prompt、skill 和规则怎么组织

业内公开实现主要有三种组织方式：

1. **仓库规则文件**：GitHub Copilot 使用仓库级、路径级指令和 review skill；规则靠近适用代码。
2. **工具级 prompt 模板**：PR-Agent 把 review、describe、improve 等工具的 system/user prompt 分开存入 TOML，并通过模板变量注入 diff、PR 描述、工单和仓库规则。
3. **多阶段 prompt chain**：Semgrep Assistant 在确定性 finding 之后分别进行分诊、修复和二次验证。

PR-Agent 的公开设计尤其值得参考：它不是为“错误、冗余、优化”各调用一次模型，而是让每个用户工具尽量只调用一次模型，以控制成本和响应时间；分类可通过配置和结构化输出调整。[PR-Agent 项目说明](https://github.com/The-PR-Agent/pr-agent)

这意味着我们之前的三个 skill 思路可以保留，但第一版不宜默认执行三次完整请求。

## 方向六：token、费用、延迟与可观测性

成熟 LLM 应用不会只保存 `total_tokens`。通常每次调用都会记录：

```text
request_id
feature / skill_id / prompt_version
model
input_tokens
cached_input_tokens
output_tokens
reasoning_tokens（如果提供）
latency_ms
provider_reported_cost（如果提供）
estimated_cost
price_version / effective_at
status / error_type
```

Langfuse 的公开方案是优先接收模型提供商返回的 usage/cost；缺少费用时，再根据模型定义中的单价计算。它同时按模型、用户、功能和 prompt 版本统计费用与延迟。[Langfuse Token & Cost Tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)

PR-Agent 也提供 LiteLLM/Langfuse/OpenTelemetry 回调，记录 token、费用、延迟、命令成功与失败；提示和响应正文不必进入遥测。[PR-Agent Observability 配置](https://github.com/the-pr-agent/pr-agent/blob/main/docs/docs/usage-guide/additional_configurations.md)

对本项目的启发：第一版直接把 DeepSeek 响应的 usage 存入 SQLite，并用带生效时间的本地价格表估算费用。不要只保存最终金额，否则价格更新后无法解释历史结果。

## 这些产品共同遇到的问题

### 1. 误报与越界建议

2026 年的一篇预印本研究了 239 个 GitHub 仓库中的 31,073 对 CodeRabbit 审查与开发者反馈。结果显示 36.4% 被接受、7.3% 引发讨论、56.3% 被拒绝；拒绝常与误报、重复、超出范围以及不符合开发者意图有关。这是单一产品的观察性研究，不能直接代表所有工具，但说明“模型能生成评论”不等于“评论值得采纳”。[研究预印本](https://arxiv.org/abs/2607.03316)

### 2. 动态语言关系图不完整

Python 的反射、装饰器、依赖注入、函数对象和运行时分派会让静态调用图产生未知边或误判。界面必须区分“已确定关系”和“推测关系”。

### 3. 行号与代码版本漂移

分析期间文件发生变化时，旧行号可能失效。每次审查结果应绑定文件内容哈希或 Git commit，并在展示前检查版本。

### 4. 被审查代码中的提示注入

代码注释、字符串、README 和测试数据可能包含类似“忽略规则”的文字。它们必须作为不可信数据分隔，不能与系统审查规则拼成同一权限层。

### 5. 成本与质量互相制约

增加完整仓库上下文、多模型调用和二次验证通常提高成本与延迟。系统需要专项/完整模式、token 预算和可测量的质量指标。

## 调研后对本项目方案的修正

### 第一版推荐架构

```text
PySide6 桌面界面
    -> 输入范围选择器
    -> Python AST/符号/导入/调用关系分析
    -> ContextBuilder 按 token 预算构造上下文
    -> 一个通用审查器 + 选中的类别规则
    -> DeepSeek 单次结构化输出
    -> 本地 Schema、路径、行号和证据校验
    -> 问题列表 + 代码标记 + 关系图 + 用量统计
```

第一版仍然保留三个规则模块：

- `correctness.md`
- `redundancy.md`
- `optimization.md`

但它们不一定对应三次 API 调用：

- 用户选“专项审查”时，只加载一个规则模块并调用一次。
- 用户选“完整审查”时，第一版把三个模块组合进一次请求。
- 论文实验阶段再增加“三个 specialist 分别调用并合并”的模式。

这样可以直接比较：

| 模式 | 预期优势 | 主要代价 |
| --- | --- | --- |
| 单次综合审查 | 快、便宜、实现简单 | 类别之间可能互相干扰，漏报较多 |
| 三次 specialist 审查 | 每类规则更集中，便于独立评估 | token、费用和延迟更高，还需去重 |
| 静态分析 + LLM | 证据更可靠、误报可控 | 本地分析器开发量更大 |

### 开发顺序也需要调整

不应先花大量时间写三个长 prompt。推荐顺序是：

1. 定义统一的 `Finding`、`ReviewResult`、`GraphNode` 和 `GraphEdge` 数据结构。
2. 实现 Python AST 项目扫描和带行号的代码分块。
3. 实现模块依赖图和基础函数关系图。
4. 实现 ContextBuilder 与 token 预算。
5. 写一个最小通用审查 prompt，打通 DeepSeek 结构化输出。
6. 再拆出 correctness、redundancy、optimization 三个规则模块。
7. 增加本地验证、反馈记录和对照实验。

## 我们可以形成的差异点

现有商业产品多围绕 PR、CI 和团队协作。本项目可以把重点放在：

- Windows 本地桌面使用，不要求先创建 PR。
- Python 项目优先，展示从模块到函数的可解释关系图。
- 每条 AI 结论回链到本地分析证据和真实代码行。
- 用户能选择上下文策略、审查类别和 token 预算。
- 清楚显示每个步骤的 token、费用、延迟和 prompt 版本。
- 用实验比较上下文选择与审查组织方式，而不把“调用 DeepSeek API”本身当作创新点。

## 当前建议

先暂停正式创建三个 skill。下一步先确认调研后的架构修正，然后创建统一数据模型和最小 AST 扫描器。skill 将在输入、输出和证据结构稳定后编写，这样不会出现提示词已经写好、程序却无法提供它所需上下文的情况。
